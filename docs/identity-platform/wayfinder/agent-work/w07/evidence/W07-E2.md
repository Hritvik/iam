# W07-E2 evidence — no database access on the signing worker

- Packet: `W07-E2`
- Agent: `OPENCODE-DS41F`
- Date: 2026-10-30

## Finding

Review 02 of W07-E showed `HumanAccessTokenIssuer.issueSafely` called
`registrations.findByAppId(...)` on the `iam-token-signer` worker. The query itself was harmless, but each in-flight
issuance needed a second pooled connection while the request transaction held one, so ~pool-minus-workers concurrent
exchanges exhausted Hikari and every request failed with `token_signing_unavailable`. It also made the signer deadline
cover a database round trip.

## Change

- `HumanAccessTokenIssueCommand` carries the pinned `RegistrationManifest` (5-arg convenience constructor retained for
  direct callers) and rejects a manifest that does not match the authorization's app/client/resource.
- `HumanAccessTokenIssuer` uses `command.registration()` when present; the registry fallback and binding verifier run
  only for direct library callers without a manifest.
- `TokenAccessIssuer.issue(...)` now takes the manifest; the orchestrator passes the manifest it already resolved on
  the request thread; `DeadlineTokenAccessIssuer` forwards it.
- The composed path therefore performs no JDBC work on the worker.

## Observed RED

Forcing the issuer back onto the registry path:

```
HumanAccessTokenIssuerTest > aManifestCarryingCommandSignsWithoutReadingTheRegistryOrBindingVerifier() FAILED
BUILD FAILED
```

The regression test mocks the registry and throws from the binding verifier, so a registry or binding lookup for a manifest-carrying command fails it. It does not exercise the adapter thread itself; reachable-JDBC is additionally established by tracing the delegate.
