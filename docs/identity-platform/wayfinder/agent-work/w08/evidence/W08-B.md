## What was built

- `V11__onboarding_intent.sql`: `append_onboarding_intent` validates the activation is ACTIVE and
  matches app/subject/versions/reason, inserts the closed event, appends the initial delivery, and
  returns `CREATED` or `EXISTING` idempotently. Security definer, fixed search path, runtime-only
  execute.
- Java: `OnboardingPayload`, `OnboardingEventFactory` (exact eight-field allowlist, deterministic
  JSON and SHA-256 fingerprint), `OnboardingIntent`, `OnboardingIntentCommand`,
  `OnboardingIntentWriter`, `JdbcOnboardingIntentWriter`, `OnboardingIntentException`,
  `SecureOnboardingEventIdGenerator`.
- The existing V2 `onboarding_payload_valid` constraint independently enforces the same allowlist,
  destination and aggregate/version binding.

## Acceptance mapping

| Criterion | Evidence |
|---|---|
| Payload is exactly the eight allowlisted fields | factory unit test parses and asserts the exact key set/values |
| ACTIVE only; app/subject/version binding | factory rejects PENDING; SQL rejects a mismatched activation |
| One logical onboarding version per activation | unique event constraint + retry returns `EXISTING` with one row |
| One initial delivery intent for the Dutch destination | `outbox_delivery` count is 1 after two appends |

## Risks

- The fingerprint is computed in Java; the DB validates its shape but not the digest itself. A parity
  test compares stored payload to the factory output.
- Composition into the activation transaction, and rollback across the two writes, is W08-C.

## Review 01 remediation

- **B-1 fixed**: `append_onboarding_intent` compares the payload's `appSubject`, `activationVersion`, `onboardingReason`, `appRegistrationId`, `activationId` and `onboardingVersion` against the activation and parameters before insert.
- **B-2 fixed**: the factory now uses the repository's canonical `OnboardingReadyPayload` + `Rfc8785PayloadFingerprint`; the unit test asserts the digest equals the canonical fingerprint of the same payload.
- **B-3 fixed**: the function requires `p_environment` to equal the app registration's environment.
- **B-4 fixed**: an existing event whose payload or fingerprint differs is rejected instead of being returned as `EXISTING`.
- The writer recomputes the canonical fingerprint from the payload and rejects a mismatch; `aFingerprintThatDoesNotMatchTheCanonicalPayloadIsRejected` proves it.
- New test `rejectsAForgedPayloadEnvironmentOrDivergentDuplicate` covers the payload, environment and divergent-duplicate checks.
- Re-verified: factory 2, integration 5.
